# Golden fixture format

Fixtures are the conformance contract for the Swift + vision port
([ADR-0002](../adr/0002-golden-python-first-swift-second.md)). Each file in
`fixtures/` pins one request and one question. The port reproduces them, and
`mlx-classifiers fixtures check` (or `mlx_classifiers.fixtures.check`) decides
whether it did. Generated by
[story 4.1](../stories/4-1-fixture-format-and-generator.md); the checker is
[story 4.2](../stories/4-2-fixture-checker.md).

```bash
mlx-classifiers fixtures generate fixtures/                       # regenerate (MLXRunner)
mlx-classifiers fixtures check fixtures/ --results results.json   # check a port
mlx-classifiers fixtures check fixtures/ --runner mlx             # determinism, in process
```

## Fixture file (`format: "mlx-classifiers-fixture/1"`)

One JSON object per file, named `<id>.json`:

| field | meaning |
|---|---|
| `format` | `"mlx-classifiers-fixture/1"`. The checker refuses any other value. |
| `id` | Case id; also the file name and the key in a results file. |
| `description` | One line on what the case exercises. |
| `model.repo` | Hugging Face repo id (`mlx-community/gemma-4-E2B-it-qat-4bit`). |
| `model.revision` | HF snapshot commit hash the weights and tokenizer came from. |
| `model.tokenizer_sha256` | sha256 of that snapshot's `tokenizer.json`. |
| `path.prefill` | Always `"split"`: MLXRunner's split prefill (see below). |
| `path.prefill_step` | Chunk size of the cache-only rows (2048). |
| `readout` | `"first-token"` or `"sequence"` (`request.options.readout`, default first-token). |
| `label_style` | `"letters"` (the normal compile) or `"option-text"`: the case runs with the wire option `options.label_style: "option-text"` (story [1.8](../stories/1-8-option-text-labels-wire-option.md); see the error case). |
| `prefix_cached` | First-token only: `true` means the system turn was KV-cached and the prompt prefilled from it. |
| `gate` | Optional; absent means `"full"`. `"answer-and-ids"`: every exact comparison below still applies (ids, images, answer, error type), but max \|dp\| and max \|dlogit\| are reported and never gated. For near-tied cases whose probabilities move by percents with one bf16 rounding step (story [4.3](../stories/4-3-per-fixture-gate-and-clear-winner-image-fixtures.md)). An unknown value fails the case. |
| `question` | Name of the request's single question. |
| `request` | The `/v1/systemone` wire request ([wire schema](wire-schema.md)), exactly one question. Image blocks carry their PNG inline as base64 (story [6.5](../stories/6-5-image-fixtures-and-battery.md)). |
| `expected` | The result block below. |
| `generator` | Package versions that wrote the file (`mlx-classifiers`, `mlx`, `mlx-lm`). Provenance only. |

### The `expected` block (= the result shape)

| field | type | compared |
|---|---|---|
| `tokens` | int[]: the whole compiled prompt, ending at the open assistant turn | exact |
| `prefix_len` | int: tokens in the cacheable system turn (0 without a `prefix`) | exact |
| `readout_position` | int: index of the last prompt token, whose logits pick the label | exact |
| `options` | string[]: option names in declared order (`["yes","no"]` for noul, `"0".."n-1"` for score) | exact |
| `labels` | string[]: the label shown for each option (`Yes`/`No`, `A`.., or the option text in sequence mode) | exact |
| `option_token_ids` | {option: int[]}: each label tokenized *in context* (after the prompt text) | exact |
| `images` | [{start, length, sha256}]: image cases only. Each image's run of soft-token ids in `tokens` (Gemma 4: `tokens[start-1]` is boi 255999, `length` x 258880, then eoi 258882) and the sha256 of its PNG bytes. A case run at a non-default soft-token budget (`options.vision_soft_tokens` 70 or 140, story [6.7](../stories/6-7-vision-soft-token-budget.md)) also records `max_soft_tokens`; at the default 280 the key is absent | exact |
| `raw_logits` | {option: float}: first-token, the logit at the option's mask id; sequence, the length-normalised loglikelihood | reported; gated only with `--logit-tol` |
| `raw_probabilities` | {option: float}: softmax of `raw_logits` at T = 1 | max abs distance within `--prob-tol` (default 1e-3) |
| `answer` | string: the option with the highest raw probability (first wins ties) | exact |
| `error` | {type, message}: present instead of `raw_*`/`answer` when compiling must fail | `type` exact; `message` ignored |

The `compared` column is the full gate; under `gate: "answer-and-ids"` the
two distance rows are reported only.

Every key present in `expected` must be present in the result; a result with
an `error` the fixture does not expect fails. On a token mismatch the checker
names the first diverging position and both ids, e.g.
`tokens[40]: expected token id 6937, got 6938` or
`option_token_ids['technical'][0]: expected token id 236799, got 99`.

## Results file (what a port writes)

```json
{
  "format": "mlx-classifiers-results/1",
  "cases": {
    "noul-first-token": {"tokens": [...], "prefix_len": 20, "readout_position": 81,
                          "options": ["yes", "no"], "labels": ["Yes", "No"],
                          "option_token_ids": {"yes": [10784], "no": [3771]},
                          "raw_logits": {...}, "raw_probabilities": {...}, "answer": "yes"}
  }
}
```

A bare `{id: result}` object is accepted too. From Python, `check(fixtures_dir,
results)` takes a path, the parsed object, or a callable `fixture -> result`
(run the port in process), and returns a `CheckReport` (`.ok`, `.render()`,
per-case `failures`, `token_ids_equal`, `max_prob_distance`,
`max_logit_distance`, `gate`). A port's checker must honour each fixture's
`gate` the same way.

## How a port computes a result

1. **Compile** with the model's chat template: system turn = `prefix`, user
   turn = rendered `state` plus the question (`prompt.render_user_turn`), the
   assistant turn opened. A JSON-object state is sorted-key, 2-space-indented
   JSON; a list state is `[1] ...` blocks joined by blank lines. An image block
   renders as `[i] ` plus `<|image>`, N x `<|image|>`, `<image|>`, with N from
   the processor's aspect-preserving resize (story
   [6.1](../stories/6-1-image-blocks-in-state.md); 256 for a square, 270 for a
   160 x 192 frame). `tokens` must match exactly; this is where template and
   tokenizer bugs show.
2. **Bind** each label in context: tokenize `prompt_text + label` (a leading
   space only if the prompt does not end in whitespace) and take the ids after
   the prompt's own. First-token mode requires one distinct id per label, else
   `LabelTokenizationError`.
3. **Prefill** on the split path, then read out. Image rows take the image's
   soft tokens (vision tower + `embed_vision`, story
   [6.2](../stories/6-2-vendor-vision-path.md)) in place of the placeholder
   embeddings, and per-layer inputs use the pad id 0 there
   ([6.3](../stories/6-3-runner-image-path.md)):
   - *first-token*: if `prefix_cached`, cache `tokens[:prefix_len]`; prefill
     the rest; logits at `readout_position` only; gather the mask ids.
   - *sequence*: cache `tokens[:-1]`; for each option prefill `tokens + ids`
     from that cache with readouts at positions `n-1 .. n-2+len(ids)`; the
     score is the mean of `log_softmax(row)[next id]` over the full vocab.
4. **Softmax** the option scores at T = 1; `answer` is the argmax.

### Why the path is pinned

Raw logits are a property of the computation, not only of the weights: the
naive `model(all)[:, -1]` and the split prefill differ by up to 0.75 in raw
logit while agreeing on argmax ([story 2.5](../stories/2-5-consumer-layers-on-readout-row.md)).
So fixtures pin MLXRunner's split prefill, and the default gates are exact
token ids plus probabilities within 1e-3, with raw logits reported rather than
gated. On the seed set, cached and uncached prefill of the same case gave
identical logits, but the cache boundary is recorded so a port can follow it.

## The seed set

Sixteen cases (`SEED_CASES` in `src/mlx_classifiers/fixtures.py`). Eight
carry images (story [6.5](../stories/6-5-image-fixtures-and-battery.md)):
a colour question on a blue square from a cached prefix, the gridworld's
action question on frame `gw-s3-t00` (`battery/images/`) given only as an
image, and a sequence-mode Yes/No on the square. Two more repeat the gridworld
case at the non-default soft-token budgets (`-vt140`: 120 soft tokens from a
480 x 576 resize; `-vt70`: 63 from 336 x 432; story
[6.7](../stories/6-7-vision-soft-token-budget.md)); the budget is in
the request's `options.vision_soft_tokens` and in `expected.images`. The three
gridworld action cases are near-tied and carry `gate: "answer-and-ids"`; three
more ask "What colour is the square that represents you?" of the same frame
at 280 / 140 / 70 (`choice-first-token-image-gridworld-you{,-vt140,-vt70}`,
`blue` by 6.1 to 6.5 raw logits) and are gated in full (story
[4.3](../stories/4-3-per-fixture-gate-and-clear-winner-image-fixtures.md)). A port
resizes to the budget (at most budget x 9 patches of 16 px, sides multiples of
48) and pools 3 x 3, exactly as at 280. The other eight: noul, choice
and score in both readout modes; a prefix-cached case; states as a string, a
JSON object and a list; a case with no system turn; sequence options of more
than one token; and `choice-first-token-multi-token-label-error`, which runs
with option-text labels (`label_style: "option-text"`, i.e. the wire option of
story [1.8](../stories/1-8-option-text-labels-wire-option.md)) and reads the
option names out first-token. `chargeback` is two Gemma tokens, so the expected result is a
`LabelTokenizationError`, with each label's in-context ids in
`option_token_ids`.

Regenerate only when the model revision, the template/tokenizer handling or
the readout logic changes on purpose. Two runs on the same machine write
byte-identical files.
